## What this file is

A reference, not a gate. Nothing in `gatekeeper.py` reads this file or enforces anything in it — it exists so the Architect (at Chunk Planning and Chunk Review, `architect_spec.md` §5b/§5c) and the Implementor (at Phase 1 Step 0a/6/7, `implementor_spec.md` §5) have a concrete, domain-specific starting point when a contract's Scientific Claim Tier is `T-COMP`/`T-CAUSAL`, when `gatekeeper.py tier-check` flags a named mathematical/statistical operator (D-037), an ablation-table row that may not isolate a single factor (D-054), or efficiency/latency/throughput claim language that may not be backed by a percentile-based measurement (D-055).

The pattern these questions share: **a test that checks input/output shape, absence of an exception, or "the numbers look plausible" does not check any of these.** Every question below is answerable only by comparing an implementation against an independent, worked-out expectation — a known-answer case small enough to verify by hand, a textbook identity, a property the real mathematical object must satisfy. Constitution C58 names this directly: a named operator needs a semantic test, not only a shape test.

Consult this file for any contract that touches the listed territory. It is not exhaustive, and it is not a substitute for actually knowing the mathematics involved — it is a prompt to ask the right question, not the answer to it.

## How to write a real semantic test, concretely

The pattern that satisfies `gatekeeper.py tier-check`'s D-037 presence heuristic *and* actually earns that presence:

1. **Construct the smallest possible input where you can compute the correct output by an independent method** — by hand, from a textbook worked example, or with a second, deliberately different implementation (a brute-force version, a library you trust, a closed-form solution for a special case).
2. **Assert against that specific, known value** — not against "runs without error," not against a property so weak that a wrong implementation could also satisfy it (e.g. "returns a matrix of the right shape" when the actual claim is about what the matrix's entries mean).
3. **Name the test so the pattern is recognizable without reading its body** — a name containing `semantic_`, `operator_`, `known_answer_`, `metamorphic_`, `invariance_test`, or the operator's own name alongside a property word (`test_laplacian_symmetric`, `test_filtration_monotonic`) is what `tier-check` looks for, but the name should be true, not just matched — don't name a shape test `semantic_test_laplacian.py` to satisfy the heuristic without the test actually earning that name.
4. **If the property is a metamorphic relation rather than a fixed known-answer** (the output should change in a specific, predictable way when the input changes in a specific way — permutation invariance, scale invariance, monotonicity under a parameter), test the relation directly: transform the input, assert the specific expected relationship between the two outputs, not just that both "look reasonable."

## ML Research

- **Does the evaluation split genuinely prevent information from the test set reaching the model** — not just at the final train/test split, but through any feature engineering, normalization statistic, or hyperparameter selection step computed before that split was applied? A normalization mean/std computed over the full dataset before splitting is a common, easy-to-miss leak.
- **Is every baseline a real, competently-tuned implementation of a real prior method** — or is at least one of them a strawman (an untuned default, a deliberately weakened variant) that makes the proposed method look better than a fair comparison would show? `factory_spec.md`'s Scientific Claim Tier / MAR-2 already requires ≥3 baselines including operational, statistical, and learned — this question is about whether each one was actually given a fair chance, not just whether the count is satisfied.
- **Does the chosen metric actually match the claim being made?** A model can have a higher accuracy while being worse at the specific thing the paper's title claims, if the metric doesn't isolate that specific property (class imbalance making accuracy misleading versus F1/AUPRC being the metric the claim actually needs; a ranking claim needing a ranking metric, not a pointwise one).
- **Was any hyperparameter, threshold, or early-stopping decision tuned using the test set, even indirectly** (choosing the reported epoch/checkpoint because it happened to score best on test, rather than pre-registering the selection rule against a validation set)?
- **Is the reported improvement distinguishable from seed variance?** Running once and reporting one number is not evidence of anything beyond that one run — the Scientific Claim Tier table's requirement for a computed CI/significance test (MAR-3) exists specifically to force this question, but the question itself is worth asking even before the statistical machinery: would a different random seed plausibly have produced the opposite ranking?
- **For any pipeline stage described as "implement X"** (a benchmark runner, an evaluation harness, a training loop): has this specific contract actually executed that pipeline and observed a result, or does its Definition of Done only confirm the machinery exists and runs without error? See `tier-check`'s operation-class-conflation warning (D-035) — the two are different claims, and a report can satisfy the letter of "implement the benchmark" without the benchmark having actually been run against real data yet.

## Topology / Geometry

Specific to the operator-identity failures this Factory's own Design Rationale trail has named — each one is a case where the code runs, returns a plausibly-shaped result, and is still not computing the thing its name claims.

- **Graph Laplacian vs. adjacency matrix**: does the implementation actually compute `D - A` (or the normalized form `I - D^{-1/2} A D^{-1/2}`), or does a variable named `laplacian` actually hold the raw adjacency matrix somewhere upstream? A known-answer test: construct a small graph (4–5 nodes) by hand, compute its Laplacian's eigenvalues by hand or with a trusted library, and assert the implementation's eigenvalues match — an adjacency matrix substituted for a Laplacian will produce visibly different eigenvalues (a true Laplacian is positive semi-definite with a zero eigenvalue for each connected component; a bare adjacency matrix generally is not).
- **Witness complex actually using witnesses**: a witness complex's simplices are determined by which *witness* points are close to which *landmark* points — not simply a simplicial complex built directly on the landmarks the way a Čech or Rips complex would be. A known-answer test: construct a small point set with landmarks and witnesses chosen so the correct witness complex differs from what a landmarks-only Rips complex would produce, and assert the implementation matches the former, not the latter.
- **Persistent homology filtration monotonicity**: a valid filtration requires simplices to appear in non-decreasing order of their filtration value (once a simplex enters, its faces must already be present, and the filtration value sequence along any inclusion must be monotonic). A test: construct a filtration and assert the monotonicity property directly (each simplex's filtration value ≥ every one of its faces' values) — not just that persistence diagrams are eventually produced.
- **Boundary operator nilpotence** (∂² = 0): if the implementation builds boundary operators/matrices for a chain complex, a real algebraic property is that applying the boundary operator twice yields zero. A known-answer test on a small simplicial complex, checking this directly, catches a boundary operator built with a sign-convention or incidence error that shape/dimension checks alone would miss.
- **Batching semantics**: does a batched computation over multiple graphs/point-clouds/windows actually treat each element of the batch independently, or does batch size >1 leak information across elements (padding artifacts changing an operator's output, a normalization statistic computed over the batch rather than per-element, a distance/neighbor computation that doesn't respect batch boundaries)? A metamorphic test: run the same input once alone (batch size 1) and once alongside other, unrelated inputs (batch size >1), and assert the result for that one input is identical either way.
- **Permutation invariance where the model/method claims it**: if a method claims invariance to node/point ordering, a metamorphic test permuting the input's order and asserting the output is unchanged (or transforms exactly as expected) is the actual test of that claim — a passing shape/type test says nothing about whether the claimed invariance holds.

## Statistics

- **Does the chosen statistical test match how the samples were actually collected** — paired (the same units measured under both conditions) or independent (different units per condition)? A paired test (Wilcoxon signed-rank, paired t-test) applied to independent samples, or vice versa, produces a number that looks like a p-value but doesn't mean what a p-value is supposed to mean here. `gatekeeper.py tier-check` flags a named test with no nearby pairing language (D-036) as a heuristic nudge toward checking this — it does not itself verify the answer.
- **Is the effect size compatible with the test** (Cliff's delta / rank-biserial for a Wilcoxon-family test; Cohen's d / Hedges' g for a t-test-family test)? Reporting a parametric effect size alongside a nonparametric test's p-value (or the reverse) is an internally mismatched pair, even when each half is individually a real, well-known statistic.
- **Is "not statistically significant" being treated as "no effect" / "equivalent"?** These are different claims. A non-significant result under-powered for the effect size actually present looks identical, in the p-value alone, to a genuinely null effect. Equivalence requires its own pre-registered margin and test (TOST / non-inferiority), not an absence of significance in the original comparison. `tier-check`'s D-036 heuristic flags this specific co-occurrence.
- **Is a multiple-comparisons correction applied when multiple hypotheses/metrics are tested against the same data** (a Bonferroni/Holm/BH-FDR adjustment, or a pre-registered composite decision rule)? Four hypotheses each tested at α=0.05 without correction has a much higher real false-positive rate than 0.05.
- **Is the confidence interval or significance test computed on the actual unit of analysis**, or on a finer-grained unit that inflates the effective sample size (treating every window/frame from a small number of underlying subjects/sessions as independent samples, when the real degrees of freedom are bounded by the number of subjects/sessions)?
- **Is any reported metric sitting on a degenerate value (exactly 0.0, 0.5, or 1.0) computed from very few samples?** `gatekeeper.py evidence-check` already flags this mechanically (SVI-007, D-027) when the backing JSON artifact's `metrics` array is populated — the question here is whether that caveat is actually surfaced in the write-up, not buried as a clean-looking number.
- **(v2.4.0) Was the sample size planned from the smallest scientifically meaningful effect size, or only checked against MAR-3's flat floor (N≥10 for a quantitative claim, N≥30 for a rate claim)?** The floor is a necessary minimum, not a sufficiency proof for every effect size. A paired-comparison planning approximation, useful as a sanity check rather than a precise requirement: at α=0.05 and 80% power, n ≈ 7.85/d², where d is the standardized effect (δ_min/σ_d — the smallest difference worth claiming, in units of the outcome's standard deviation). A standardized effect around 0.3 needs roughly 88 paired observations to distinguish reliably from noise — MAR-3's floor of 10 clears the structural check but is not automatically adequate for a small claimed effect. If `venue_requirements.md`'s Minimum Meaningful Effect Size table states a value, use it here; if the planning sample size this implies is far above what's actually available, that is worth surfacing as an MAR-3 finding now, not discovering as an underpowered result later.
- **(v2.4.1) For every hyperparameter D-018 flags as needing a sensitivity analysis, is a stability curve actually reported** — at minimum ±10%, ±25%, and ±50% perturbations around the chosen value, plotted against the target metric — or does "needs a sensitivity analysis" stop at being named in `venue_requirements.md` without a reported curve ever following it? D-018 requires naming *which* hyperparameters need one; this question is about whether the protocol itself actually ran.
- **(v2.4.1) For every reported error bar, is the variability source named** (train/test split? initialization? a random parameter draw? the full run under fixed conditions?), the computation method stated (closed-form, bootstrap), and the interval width declared as 1-sigma or 2-sigma — or is a bound reported without saying what it's a bound *on*?
- **(v2.4.1) In the common few-run regime (N<10), is an Interquartile Mean + stratified bootstrap CI used** rather than a plain mean ± std? Agarwal et al. (NeurIPS 2021 Outstanding Paper) found ordinary per-run standard deviation poorly justified at small N, and IQM needs fewer runs than the median for equivalent CI width while staying far more outlier-robust than the mean.
- **(v2.4.1) Does the reported variance come from seed alone, or from spreading a fixed run budget across seed + data-split + augmentation + initialization?** Bouthillier et al. (MLSys 2021) found seed is not the largest source of variance, and for a *fixed* compute budget, spreading runs across more distinct variance sources gives a measurably more accurate variance estimate than repeating one source — by their measurement, roughly 51× more compute-efficient.
- **(v2.4.1) Is a seed-only distribution reported separately from the searched-hyperparameter-and-seed-jointly distribution** (fixing the winning hyperparameter configuration and varying only the seed across N runs), so a reviewer can see what evaporates under a different seed draw alone, holding the rest fixed? And is total project compute reported, including failed and preliminary runs — not only the compute behind the runs that made it into the final table — since a large hidden search inflates the apparent effect size of what's shown?

## Theory-Adjacent Standards (v2.4.1 — skip if no formal theorem/proof is in scope)

Consult whenever a contract's claim rests on a formal, formula-based, or mathematically-derived
proof. `dynamic_rules.md`'s D-003 already requires that any such proof pin the exact numeric
parameters it's evaluated against (a `Verification Parameters:` block), so two independent runs
of the same contract can't quietly use different numbers and both claim PASS — that's
verification-*reproducibility*. This section is about a different, earlier concern: whether the
proof as *written* is actually complete enough for a skeptical reader to follow.

- **Is the full assumption set for this theorem stated explicitly at the point the theorem is introduced**, or is a needed assumption only implied by context or buried in a later section?
- **Is a complete proof present** — in the main text if short, in the supplement with an explicit proof *sketch* left in the main text if long? A theorem with no proof and no sketch anywhere invites exactly the skeptical, line-by-line adversarial read that a clear sketch would preempt.
- **If this theorem also has a D-003 Verification Parameters block because it's checked computationally, is the written proof's completeness being treated as a separate question** — not assumed to be covered by the computational check passing?

## Hardware / Efficiency Claims (v2.4.0)

Consult whenever a contract's claim touches latency, throughput, real-time behavior, memory footprint, or any other computational-efficiency property — see `venue_requirements_TEMPLATE.md`'s Efficiency Claim Requirements section, which this checklist backs.

- **Is any latency number reported as a mean rather than a percentile distribution (p50/p90/p99)?** A mean can hide a bad tail, and a real-time system is broken by its tail, not its average. If only a mean is available, say so explicitly rather than letting a single "average latency" figure stand in for the distribution.
- **Is throughput reported at a realistic batch size, separately from batch=1 latency** — or is a single number being asked to answer both questions? The two measure different things and a system can be strong on one and weak on the other.
- **Is the hardware/software stack named specifically** (exact accelerator model, driver and framework versions, warm-up iterations explicitly excluded from timing) — or is "on a GPU" standing in for a number nobody else could reproduce?
- **Is peak memory reported separately for training and inference**, and does it include activation memory, not only parameter count? Parameter count alone systematically underestimates real footprint for most architectures.
- **If a FLOPs/MACs number is the only efficiency evidence, is it being treated as a measured latency claim rather than an unvalidated proxy?** Two architectures can be FLOP-matched and parameter-matched while diverging sharply on real hardware latency, because of how well each shape actually parallelizes on real hardware — FLOPs is one axis worth reporting, never a substitute for a measured number.
- **For edge or thermally-constrained hardware, is behavior tested under sustained load**, not a short burst? Throttling changes latency/throughput numbers measured over minutes versus seconds, and a single quick benchmark run can miss this entirely.
- **Does the project have a `hardware_profile_manifest.json` (D-056) backing this claim**, or is the efficiency number only asserted in prose with nothing else to check it against?

## Ablation Design (v2.4.0, extended v2.4.1)

Consult for any contract whose Verification Scripts or Definition of Done include an ablation study — removing or varying one component to attribute an effect to it. `venue_requirements_TEMPLATE.md`'s Required Ablation Types section states *which categories* apply to a project; this checklist is about whether any one ablation *row* is actually valid evidence.

- **Does this ablation row change exactly one factor relative to the baseline row** — or does removing the named component also change parameter count, compute budget, augmentation, or training schedule? If more than one thing changed, the result cannot be attributed to the named component alone; report which factors covaried, and re-run holding the others fixed if the ablation is load-bearing for a title or abstract claim.
- **If more than one component could interact, is that interaction actually tested** (a small factorial design, or at least a stated argument for why interaction is implausible here) — or does the paper only show single-component removal, silently assuming no interaction effects exist?
- **(v2.4.1) If N components are too many for a full factorial design (compute-prohibitive), is there at minimum a leave-one-out table *plus* a cumulative/incremental ablation** (components added one at a time, in a stated and justified order)? Leave-one-out alone can only show that removing each component hurts a little — it cannot detect synergy, which is a different claim. A stated narrative of "these components are complementary/synergistic" needs at least one path through the interaction space to back it, not single-component removal alone.
- **(v2.5.0) For N ≤ 4 components, is a full 2^N factorial design executed?** Encode factors as x_i ∈ {-1, +1} and fit y = β_0 + ∑ β_i x_i + ∑_{i<j} β_{ij} x_i x_j + ... to mathematically separate main effects β_i from interaction/synergy effects β_{ij}. A simple leave-one-out table cannot distinguish a component with zero main effect that masks a negative interaction from a truly vital component.
- **Was any hyperparameter re-tuned for the ablated variant, or is it running under the full model's tuned hyperparameters even though the ablated variant might have a different optimum?** These answer different questions — does removing X hurt the *architecture*, or hurt *this specific tuning* — and a single ablation number conflates them unless the report says which one it's answering.
- **Is the factor(s) held fixed for this row stated explicitly nearby the result** (in the contract report or the ablation table's own notes), or does the reader have to infer it from the diff? `gatekeeper.py tier-check`'s D-054 heuristic looks specifically for this declaration and flags its absence — see the note on what it can and can't actually verify.

## Generalization & Stress-Testing (v2.4.0, extended v2.5.0)

Consult whenever a robustness, generalization, out-of-distribution, or adversarial-robustness claim is made — the same STRONG signal set `tier-check` already uses to infer `T-CAUSAL` (`robust to`, `generalizes to unseen/out-of-distribution`, `invariant to`, `adversarial`) is a good self-check for whether this section applies.

- **Is degradation tested across a severity ladder, or only at one implicit severity?** Define the domain's corruption taxonomy at multiple severities (for streaming/time-series: clock skew, dropped or reordered samples, sensor drift, quantization noise; for tabular/graph: label noise, missing-feature rate, adversarial node/edge injection) and report a severity-aggregated error rather than a single "robust accuracy" number that hides *where* it degrades.
- **If a cross-domain or cross-dataset transfer claim is made, does the shift satisfy all three of:** a real, substantial in-vs-out-of-distribution performance gap; motivation from a genuine deployment scenario, not an arbitrary synthetic perturbation; and solvability in principle (not so extreme that no method could plausibly bridge it)? A shift too mild to matter and a shift no method could survive are both uninformative, for opposite reasons.
- **If the claim touches security or safety, is adversarial robustness reported as a curve** (accuracy vs. perturbation budget ε, multiple budgets), not a single point? A single "robust to attack X" claim without a budget curve hides exactly how much robustness actually exists.
- **(v2.5.0) Is a structured Failure Case Taxonomy included?** Characterize failure modes across demographic, sensor, temporal, or geographic subgroups. Identifying where and why the model breaks increases credibility; hiding failure modes invites immediate reviewer attack.
- **If robustness testing is genuinely out of scope for this project, is that stated explicitly in Limitations rather than left silently unaddressed?** An acknowledged gap reads better to a reviewer than a discovered one — the same logic Constitution C51 applies to a project's methodology generally.
